# Delay Intelligence: last-mile delhivery capstone

Predicts delivery hours, flags parcels likely to miss their promised window, segments the 24 hubs by how they really
operate, and turns the 48 parcels about to be dispatched into an action list. Money is in Indian Rupees (INR).
Promised hours: Express 36, Standard 60, Economy 96. A parcel is delayed when `delivery_hours > promised_hours`.

## How to run

From a fresh clone (Python 3.11 or newer; only pandas, NumPy, scikit-learn and joblib are used, fully offline):

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python generate_data.py            # prints: 24 1224 48  (writes the three CSVs into data/)
python part_a_clean_eda.py         # cleaning, data/modelling_table.csv, delay evidence
python part_b_regression.py        # delivery-hours regression
python part_c_classification.py    # delay classifier, feature signal, tuning, alert threshold
python part_d_segments.py          # hub profile and K-Means segments
python package_model.py            # refits the final model, writes models/ and the reload check
python predict_delay.py            # scores data/new_shipments.csv -> outputs/new_shipment_actions.csv
```

`models/delay_model.pkl` is regenerated by running `python package_model.py`. The committed pickle loads reliably only on
the scikit-learn version pinned in `requirements.txt` (pandas 3.0.2, numpy 2.4.4, scikit-learn 1.8.0, joblib 1.5.3), so
if your installed versions differ, re-run `package_model.py` instead of loading the committed file. Every random step
uses `random_state=42`; running a script twice gives identical files.

| Path | Purpose |
|---|---|
| `generate_data.py` | The provided data generator, committed verbatim |
| `src/shipment_prep.py` | `PROMISED_HOURS`, `FEATURES`, `NOISE_COLUMNS`, `clean_shipments`, `build_features` and small shared helpers |

## Data findings

Cleaning: 24 exact duplicates were removed (1224 raw rows to 1200); the
`service_type` column had 12 spellings and now has 3;
5 weights above 100 kg were scanner faults and were treated as missing. Gaps were filled with
medians computed once on the full history: distance 314.95 km, weight 1.83 kg,
declared value INR 1,121.50. The modelling table has 1200 rows and
0 missing values in the features and targets. Overall 278 parcels were
delayed (delay rate 0.2317).

1. **Express is delayed most often.** Its delay rate is 0.4897 (119 of
   243), against 0.2056 for Standard and 0.0857 for Economy.
   The tightest promise leaves the least slack.
2. **Delay rises sharply with hub tier.** It is 0.04 for Tier 1, 0.215 for Tier 2 and
   0.44 for Tier 3.
3. **Delay explodes with distance.** By distance band the delay rate is 0.0219 (0-200 km),
   0.1368 (201-400), 0.4364 (401-600) and
   0.8523 (601+ km).
4. **Strongest correlations with `delivery_hours`** (from `part_a_correlations.csv`): `promised_hours` (+0.8372), `distance_km` (+0.4013), `n_stops` (+0.3247).
   `promised_hours` is high mostly because Economy parcels are promised, and take, longer; it is not a cause of delay by itself.
5. **Why declared value was log-transformed.** On the filled column the mean is INR 1,533.05 against a median of
   INR 1,121.50, a long right tail; after the log the mean (7.0277) and median
   (7.0224) are almost equal, so the feature is roughly symmetric.

## Model results (regression)

Split: 840 training / 180 validation / 180 test rows. The scaler was fitted on training rows only
(`train_scaled_max_abs_mean` = 0.0 while the test rows give 0.2187, which shows no leakage).

- **Baseline.** Predicting the training mean gives validation R2 -0.0212 (RMSE 18.8552 hours):
  it explains none of the variation, so every real model must beat this.
- **Validation winner.** `linear_regression` has the lowest validation RMSE, 4.8912 hours
  (R2 0.9313), essentially tied with gradient boosting (4.9165 hours,
  R2 0.9306); random forest scored 5.5095 and the decision tree 6.2796.
  Scored once on the test rows, the final model reaches RMSE 4.5235 hours and R2 0.9493.
- **Bias versus variance (tree depth).** Depth 1 is high-bias: train RMSE 11.6334 and validation RMSE 12.1324 are
  both high and close together (depths 2 and 3 are still underfit). With no depth limit, train RMSE is 0.0 but
  validation RMSE is 7.8368: high variance (depth 12 shows the same pattern: 1.3613 versus 7.354).
  The best depth is 6 (validation RMSE 6.2796).
- **Learning rate.** For gradient boosting with 100 trees, 0.1 is best (validation R2 0.9306). At 0.01 (R2 0.7127) each
  tree corrects too little, so 100 trees are not enough (too slow, underfit); at 1.0 (R2 0.844) each tree applies its full correction and
  overshoots, chasing noise.
- **Cross-validation disagrees with validation.** On the 1,020 training-plus-validation rows, gradient boosting scores mean R2 0.9353
  (std 0.0045) against 0.9261 (std 0.0048) for linear regression.
  I would ship **gradient boosting**: the validation gap is tiny (0.025 hours on one 180-row split), while
  the cross-validated gap uses five folds and favours boosting, which can also capture interactions such as a sale hitting Express parcels harder or rain on long lanes. Linear regression is the simpler
  fallback. Following the protocol, only the validation winner was scored on the test rows, once.

## Model results (classification)

Split: stratified 840 / 180 / 180 with 195 / 42 / 41 delayed parcels.

- **Blind baseline.** Predicting "on time" for everything gets validation accuracy 0.7667 but recall 0.0:
  it never catches a delayed parcel (FN 42), so it is useless for the one job we need. Trained models reach F1 of
  0.8046 (logistic regression), 0.747 (decision tree, depth 6) and 0.7848 (default forest).
- **Noise columns.** The five bookkeeping columns hold 0.2245 of the 17-column forest's importance (a forest splits on noise when it is offered it),
  yet all five rank 8th or lower by F-score (label_print_batch 4.5847, scanner_build_no 0.023, tape_roll_no 1.9052, sticker_serial_mod 1.2776, shelf_slot_no 0.1393), all below 10, while the weakest of the top seven
  (`sale_event_flag`) has F-score 36.7281. The top seven are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`,
  `promised_hours`, `rain_flag` and `sale_event_flag`.
- **Choosing k.** Validation F1 by k: 5 -> 0.6988, 7 -> 0.8333, 10 -> 0.7857, 12 -> 0.8049, 17 -> 0.7848. Five columns drop real signal; more than seven let noise back in. k = 7 was used.
- **Tuning did not beat the untuned forest.** Validation F1: grid search 0.775, randomized search 0.7848, default forest on the same 7 columns
  0.8333, although the searches reached cross-validated accuracy 0.8952 and 0.8905.
  With only 42 delayed parcels in validation, one parcel moves F1 by a few hundredths, so these gaps are within noise and tuning on a 180-row validation set mostly tunes to that sample.
  The final model is therefore the default forest (n_estimators 100, max_depth unlimited, min_samples_leaf 1) behind the k = 7 selector.
- **Alert threshold = 0.5.** Because a missed delayed parcel costs more than an unnecessary call, the rule is the highest threshold with validation recall of at least 0.80.
  At 0.5 validation recall is 0.8333 with precision 0.7955; at 0.6 recall falls to 0.7619 (precision 0.8889), breaking the rule,
  while 0.4 would raise recall to 0.881 at precision 0.74.
- **Test result (scored once).** Precision 0.6889, recall 0.7561, F1 0.7209 (TP 31, FN 10, FP 14). Test recall is lower than validation recall
  (0.8333); with only 41 delayed parcels in the test set, a few parcels swing recall by several points, so the 0.80 recall target should not be promised to the business.

## Operations recommendation

**Escalate segment.** K-Means with K = 3 on four hub-level measures gives Standard (7 hubs, delay rate 0.0257),
Watch (8 hubs, 0.155) and Escalate (9 hubs, 0.46). The Escalate hubs are: HUB13 Nagpur (delay rate 0.46); HUB15 Kochi (delay rate 0.36); HUB17 Patna (delay rate 0.46); HUB18 Ranchi (delay rate 0.38); HUB19 Guwahati (delay rate 0.62); HUB20 Raipur (delay rate 0.48); HUB21 Bhubaneswar (delay rate 0.4); HUB23 Siliguri (delay rate 0.44); HUB24 Agartala (delay rate 0.54).

**Tier labels that mislead.** 4 hubs behave unlike their tier label (`tier_vs_segment_mismatch.csv`):

- HUB07 Kolkata: tier 1 label, but behaves as **Watch** (delay rate 0.14, mean distance 304.736 km, mean stops 70.76).
- HUB13 Nagpur: tier 2 label, but behaves as **Escalate** (delay rate 0.46, mean distance 473.32 km, mean stops 83.92).
- HUB15 Kochi: tier 2 label, but behaves as **Escalate** (delay rate 0.36, mean distance 466.514 km, mean stops 84.1).
- HUB22 Dehradun: tier 3 label, but behaves as **Watch** (delay rate 0.2, mean distance 316.738 km, mean stops 73.28).

The tier label (a size and capacity label) should not be used to decide escalation or staffing; use the behavioural segment instead, and review these four hubs individually.

**Alert rule.** Flag a parcel when its delay probability is at least 0.5. From `part_c_final_test.csv`, of every 10 flagged parcels about 6.9 are really delayed
(precision 0.6889), and of every 10 delayed parcels about 7.6 are caught (recall 0.7561).

**New parcels.** Of the 48 new parcels, 8 were flagged; 6 of those sit in Escalate-segment hubs and need a hub-manager escalation, and 2 get a proactive customer call (`new_shipment_actions.csv`).

**Why K = 3.** Operations runs exactly three playbooks, and the evidence supports it. The across-to-within distance ratio is 2.894 for K = 2 and 5.3928 for K = 3 (sizes 9-8-7),
rising to 6.3047 (sizes 8-7-5-4) and 6.8866 (sizes 8-7-4-3-2) for K = 4 and 5. The ratio keeps rising with K almost by construction, and those
solutions contain clusters of fewer than 6 hubs, too small to carry their own playbook, so K = 3 is kept.

## Production plan

**(a) Production-readiness characteristics mapped to this repository**

| Characteristic | Where it lives |
|---|---|
| Accuracy | Held-out results in `outputs/part_b_metrics.csv` and `outputs/part_c_final_test.csv` |
| Reliability | `clean_shipments` handles duplicates, blank values and the 999 kg sentinel; `predict_delay.py` asserts no missing model inputs |
| Reproducibility | `generate_data.py`, fixed `random_state=42`, pinned `requirements.txt`, byte-identical reruns |
| Maintainability | One shared module `src/shipment_prep.py`, one script per Part, a documented run order |
| Consistency | Training and prediction both use `clean_shipments` / `build_features`, the stored `impute_values.csv` medians and `feature_order.csv` |
| Monitorability | Per-parcel `delay_probability`, `flagged` and `action` are written to a CSV; `part_d_reload_check.csv` verifies the saved model |
| Performance (speed) | The packaged pipeline scores a whole batch with one `predict_proba` call (no retraining at scoring time) |

**(b) What to monitor, with triggers**

- Weekly delayed share of delivered parcels: baseline 0.2317; investigate if it is above 0.30 or below 0.17 for two weeks in a row.
- Weekly share of parcels flagged: on validation at threshold 0.5, 9 false alarms plus 35 true alerts were raised on 180 parcels (about 24%); investigate if the weekly share leaves 15% to 35%.
- Recall on parcels whose outcome is now known: validation 0.8333, test 0.7561; trigger a review if it falls below 0.65 over a month, and retrain if precision falls below 0.55.
- Input drift: median `distance_km` (history 314.95 km) moving by more than 15%, or the share of 999 kg sentinel weights rising above 1%.

**(c) Retraining and the sale window.** Retrain monthly on all parcels with known outcomes by re-running `part_a` to `package_model.py`, and promote the new model only if it beats the current one on the most recent two weeks. Retrain early whenever a trigger above fires.
The 15-28 September sale window (`sale_event_flag`) should be compared with the same kind of event, the previous sale, never with ordinary weeks, because delays are expected to spike during a sale; ordinary-week baselines should exclude it.
Drift here would look like new lanes with different distances or stop counts, a changed Express share or cash-on-delivery share, hubs changing their operating behaviour (as the four mismatched hubs already do), or a rising share of faulty scanner readings.

## Limitations

- The data is synthetic, so the clean signals (for example the strong distance effect) will be weaker and messier in real operations.
- The test set has only 41 delayed parcels, so test precision, recall and F1 are noisy; the gap between validation and test recall shows it.
- The alert threshold and the final configuration were chosen on a single 180-row validation split with 42 delayed parcels, so another split could pick a different threshold or model.
- Splits are random, not by time; a real deployment predicts the future, so results may be optimistic and a time-based split should be tested.
- Each hub has only 50 historical parcels, so hub profiles and K-Means segments are noisy; the sale effect rests on one 14-day event.
- Probabilities are not calibrated, and the required 17-feature list keeps five noise columns that carry no real signal.
